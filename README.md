# Практическая работа: CI для веб-проекта

Тема 3.1.43. Назначение CI/CD при автоматизации веб-проектов.

## Проект

- index.html — главная страница.
- style.css — оформление.
- script.js — обработчик кнопки.
- .github/workflows/ci.yml — автоматическая проверка файлов.

Для просмотра откройте index.html в браузере и нажмите кнопку проверки JavaScript.

## Рабочий процесс

При push в ветку main запускается Web Project CI. Шаг Get project files получает содержимое репозитория; Check project files выполняет:

```bash
test -f index.html
test -f style.css
test -f script.js
```

Проверяется только наличие файлов. Проверка синтаксиса, сборка и публикация сайта в этом задании не настроены.

## Эксперимент

1. [Первый запуск](https://github.com/Aziz0478/my-ci-project/actions/runs/43360230300) — Success: все три файла присутствуют.
2. script.js переименован в script-test.js. [Второй запуск](https://github.com/Aziz0478/my-ci-project/actions/runs/43360309952) — Failure на шаге Check project files, код завершения 1.
3. Исходное имя script.js восстановлено отдельным коммитом. Результат нового запуска доступен во вкладке Actions.

## Ответы на вопросы

1. **Какое событие запускает CI?** Отправка изменений (push) в main.
2. **Какие файлы проверяются?** index.html, style.css, script.js в корне репозитория.
3. **Как отображается успех?** Зелёная отметка и статус Success; команда проверки возвращает код 0.
4. **Как отображается ошибка?** Красная отметка и статус Failure. В эксперименте шаг проверки завершается с кодом 1 из-за отсутствия script.js.
5. **Чем полезна проверка для команды?** Она автоматически применяет одинаковые правила к изменениям всех участников, выявляет забытые файлы и сокращает ручную работу.

## Вывод

GitHub Actions позволяет проверять структуру веб-проекта при каждом push. Эксперимент показывает, как CI обнаруживает отсутствие обязательного файла. CI не гарантирует правильность всего приложения: качество результата зависит от настроенных проверок.
